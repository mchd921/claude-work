# 新しいブロックを追加する

追加するブロック: $ARGUMENTS

（空なら、どんなブロックにするかをユーザーに聞く。）

## 1. 仕様を決める

次の5つを決めて、実装する前にユーザーへ短く示す。はっきりしない点は、もっともらしい案を選んで「こうしました」と書く。質問で止めるのは、遊び方が大きく変わる場合だけにする。

- **名前**（`type` の値。英小文字。例 `bomb`）と、画面での見た目（色、印）
- **当たったとき**に何が起きるか
- **出てくるステージ**と数（例: ステージ2から、1ステージに2個まで）
- **スコア**
- **クリアの条件にどう関わるか**（壊せないブロックは、クリアの判定から外す必要がある）

## 2. 実装する（すべて `index.html` の中）

1. ブロックに `type` がなければ、`buildLevel()` の `bricks.push` に `type: 'normal'` を追加する。
2. `buildLevel()` で、新しいブロックを置く。置く位置は `Math.random()` ではなく `level`・`r`・`c` から決める（テストで結果が毎回同じになるように）。
3. `update()` のブロックの当たり判定で、`b.type` によって動きを分ける。
4. `draw()` のブロックの描画で、見た目を分ける。

守ること（CLAUDE.md の「構成」より）:
- 座標は 480×640 のゲーム内座標を使う。速さや時間は `f` を掛けて計算する。
- 1回の分割移動で当てるのは最大1ブロック（`break` を消さない）。周りのブロックを壊す効果は、当たったブロックの処理の中でまとめて行う。
- クリア判定 `bricks.every((b) => !b.alive)` を壊さない。壊せないブロックがあるなら、それを除いて判定する。
- 画面に出す文字は日本語。iPadのタッチ操作の処理には手を入れない。

## 3. テストを足す（`tests/check.mjs`）

最低限、次の2つを `check(...)` で追加する。
- **出てくるか**: 対象のステージで `game.bricks` に新しい `type` があり、それより前のステージにはない。
- **効果があるか**: そのブロックにボールを当てたときの結果を確かめる。ボールの位置と向きは `game.ball` に直接入れてよい（例: ブロックの真下に置いて `vy` をマイナスにし、数フレーム進める）。

すでにある「どのステージでもブロックが画面内に収まる」と「ステージ1をクリアできる」が通り続けることも確かめる。

## 4. テストが本当に効くか確かめる

新しいブロックの処理を**わざと壊したら、新しいテストが失敗する**ことを確かめる。

```bash
bash .claude/skills/add-block/mutate.sh 's/壊す前の文字列/壊した後の文字列/'
```

`mutate.sh` は `index.html` のコピーを壊してチェックを実行する。本物のファイルは変わらない。「見逃した」と出たら、テストを強くしてやり直す。

## 5. 報告する

最後に、次の3つを短く報告する。
- 追加したブロックの仕様（1. の5項目）
- 追加したテストと、`mutate.sh` で確かめた結果
- iPadで遊んで確かめてほしいこと（見た目が分かりやすいか、ちょうどいい難しさか、など）。ここだけは人間にしか確かめられない。
